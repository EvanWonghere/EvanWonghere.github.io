> “AI 负责写代码，人类则作为人类在环的‘编排者’。”

如今，整个行业都在热炒这种论调：传统的代码编写方式已经奄奄一息，**规范驱动开发（Spec-Driven Development，SDD）** 才是未来。你先生成一份计划，然后便不再亲手写任何代码。智能体比你更懂实现，所有实现工作都交给它们。你只需以*专家*的身份提供所谓的“好品味”，审查产出，并不断引导智能体按照你精心制定的计划执行。

如今，这套工作流已经演化出许多形态，但总体而言，流程都是：有人定义项目需求（从宏观到微观，同时兼顾两个层面），生成计划，然后[一次又一次地拉动老虎机的拉杆](<https://blog.quent.in/blog/2026/03/09/one-more-prompt-the-dopamine-trap-of-agentic-coding/>)，反复迭代，有时还会同时运行多个智能体实例，直到任务完成。在整个过程中，“编排者”与那些正在生成并提交的代码之间的距离，越来越远。

编程智能体（Coding Agent）确实有用，也确实强大。但它们已经带来了一些可以衡量、值得讨论的代价：

- 为了应对 AI 非确定性所带来的额外不确定性，周边支撑系统必须变得更加复杂。
- 相当一部分人的技能正在退化。
- 个人乃至整个团队受到供应商锁定（vendor lock-in）的影响。（Claude Code 一旦宕机，已经出现过整个团队工作停摆的情况。）
- 使用工具的费用不断波动并上涨。雇员成本相对固定，Token 成本却始终充满变数。

要想真正用好这种编程智能体工作流，关键在于一个极其重要的前提：**只有具备扎实经验、能够进行批判性思考，并且能自如地在软件架构层面工作的开发者，才可能在几千行生成代码中的问题酿成后果*之前*发现它们。**

但命运偏偏开了个讽刺的玩笑：已有研究表明，AI 工具恰恰会对人的批判性思考能力和思维清晰度[产生负面影响](<https://margaretstorey.com/blog/2026/02/18/cognitive-debt-revisited/>)。

## 不只是又一层“抽象” {#section-1}

社区里有个很常见的说法：程序员只不过是在“往技术栈上层走”，转向另一种抽象形式罢了。但这些工具究竟能否算作一个抽象层，本身还没有定论。**不确定性变得更高，并不等于抽象层级变得更高。**

暂且把这个争议放到一边，程序员确实向来对新语言、新编程方式心存戒备。当年 FORTRAN 问世时，程序员同样持怀疑态度。他们提出过类似的担忧：它可能引入更多 Bug 和不稳定性，直接写汇编反而更高效。后来，围绕编译器的普及，也有人争论它会不会给开发过程引入太多不可见的“魔法”。这些争论本质上是规范性判断：人们担心，一旦接纳了新技术，某些东西*可能*会因此失去。

但今天的不同之处在于，过去那些担忧主要还停留在猜测和理论层面。而 AI 工具出现不过短短几年，我们已经开始看见显著影响。受影响的*不只是初级开发者*，甚至包括拥有十年乃至更长经验的人：

### 这一次，确实不一样。 {#section-3}

当一名 C++ 开发者转向 Java 或 Python 时，他们并没有抱怨自己变得脑子不清楚。当一名系统管理员开始使用 AWS 时，他们也没有觉得自己正在失去理解网络的能力。

资深工程师转向管理岗位、写代码的机会减少，久而久之编码手感生疏，这并不是什么新现象。过去，这是一条自然而然的专业成长路径：一名工程师积累了几十年的编码实践、摸索与磨炼，有足够的时间和经验，将技能和判断沉淀下来。等工作重心从具体语法转向更高层次的架构决策时，他就能运用这些经验。然而，这样的人本来就极为稀少。如果我们所有人都不再经历亲手编写代码、解决问题、调试程序所带来的磨炼，下一代资深工程师又从哪里来？

而当下的趋势却是：那些还没来得及积累长期实践经验、没经历过三十多年摸索与磨炼的开发者，被直接推向更高层级的工作流，要求他们拿出资深工程师花了几十年才获得的技能，去管理 AI 智能体。

不过，资深工程师也无法幸免。拥有近三十年开发经验的 [Simon Willison](<https://simonwillison.net/2026/Feb/15/cognitive-debt/>) 也曾表示，他已经缺少一个“关于应用究竟能做什么、又是如何运作的牢固心智模型。这意味着每增加一项功能，推理它的难度都会进一步提高”。

## “熟练的编排者”悖论 {#section-4}

Anthropic 最近的一项[研究](<https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic#and-less-hands-on-practice>)里，谈到频繁使用编程智能体的风险时，有一段出人意料的坦诚表述：

> 编码技能的退化之所以令人担忧，原因之一是“监督悖论”……有效使用 Claude 需要监督，而监督 Claude 恰恰需要那些可能因为过度使用 AI 而退化的编码技能。

LinkedIn 的软件工程总监 Sandor Nyako 管理着 50 名工程师。他已经注意到这种现象正在组织内部蔓延，因此要求团队不要在“需要批判性思考或问题解决能力的任务”中使用这些工具。[来源](<https://www.businessinsider.com/leaders-worry-about-skill-atrophy-due-to-ai-adoption-2025-10#8786254a-3fe1-4407-98a2-7c2eaac66b6f>)

> “人要想提升技能，就必须经历困难。他们必须锻炼自己独立思考、把问题想透的能力。”他说，“如果一个人没有批判性思考能力，又怎么判断 AI 说得对不对？”

另一个问题是，究竟怎样才算“过度使用”？我们已经有[数据研究](<https://www.anthropic.com/research/AI-assistance-coding-skills>)和[个人经历](<https://www.youtube.com/watch?v=pzkwn3hu1Cc>)表明，这些技能可能在相当短的时间内退化甚至流失，有些案例只需要几个月。

这就是让许多 AI 鼓吹者陷入自相矛盾的地方：**编程智能体的使用，正在削弱有效管理编程智能体所必需的技能。**

## 大语言模型加速了错误的环节 {#section-5}

与当下盛行的说法恰恰相反，我们未必*需要*更快地写出代码。尤其是那些我们没有完全理解的代码，更何况是大批量生成、根本无法在合理时间内审查完的代码。

### 在 AI 出现之前，一名优秀开发者的优先事项可能是： {#section-6}

1. 理解代码，以及它与整个代码库的关系。
2. 确保代码符合既定文档和高效、合理的工程规范。
3. 在不牺牲可读性的前提下，用尽可能少的代码完成目标。
4. 交付速度。

### 智能体编程，以及大语言模型总体上的使用方式，几乎把这张清单彻底颠倒了。 {#section-7}

它们的能力展示和实际用法，往往聚焦于速度：在固定时间内生成更多代码。速度原本是高水平能力的自然结果；如果强行追求速度，就总会牺牲准确性。而这些工具的集成方式，很少把更深入的理解或更精炼的实现放在首位。

这些工具能不能按这样的方向使用？能。只要愿意下功夫，当然可以。

但人们真的这么用了吗？恐怕并没有。组织内部强制推行 AI，以及围绕 [Token 用量的狂热宣传](<https://www.pymnts.com/artificial-intelligence-2/2026/ai-adoption-is-being-measured-in-tokens-but-the-metric-falls-short-experts-say/>)，已经很能说明问题。

## 写代码 === 做规划 {#section-8}

开发者之间其实还有一道不那么常被提起的分野：**我们中的一些人，恰恰是在写代码的过程中，才能更好地规划与思考。** 用代码思考、在代码中工作，绝不是毫无意义的苦差事。它迫使你从技术层面思考问题，涵盖安全性、性能、用户体验以及可维护性等方方面面。

最近，在一次讨论“规范驱动开发”的[访谈](<https://youtu.be/IGsbARhERqc?t=501>)中，开源编程智能体 OpenCode 的创造者 Dax（没错，他自己就做了一个开源 Coding Agent）说过：

> “当我着手做一件新事情，或者一件很有挑战性的事情时，亲手敲代码，就是我弄清楚**我们到底应该做什么**的过程。要我坐在那里，写一份巨长的规格说明，精确规定功能应该如何运作，我真的很难做到。
>
> “我喜欢先写类型定义，喜欢写出几个函数可能怎样协同工作，也喜欢摆弄文件夹结构，看看不同概念应该如何组织。我认为，绝大多数程序员其实一直都是这样做事的。我看不出自己有什么充分理由要放弃这种方式，因为我就是靠它来弄清楚该做什么的。”

**你说出口的，往往并不完全是你真正想表达的。** 大语言模型会自行用假设（或幻觉）填补歧义。结果就是：需要更多代码审查、更多智能体修改、消耗更多 Token，而且你与实际造出来的东西越来越脱节。反过来说，即使你写出了一份自认为美得无可挑剔、毫无歧义、结构完美的提示词，大语言模型仍可能编造出一个根本不存在的方法。因为从根本上说，它是一个预测下一个 Token 的引擎，而不是编译器。你不能拿概率性系统替代确定性系统，却又指望它完全不存在歧义。

即使是那些最热衷 AI 的[资深开发者](<https://www.youtube.com/watch?v=cv6rwHTGT5w>)，也已经开始意识到这种脱节正在变成一个迫在眉睫、而且不断扩大的问题。

## “供应商锁定” {#section-9}

前段时间 Claude 服务中断时，我在 LinkedIn 上看到[不少帖子](<https://www.linkedin.com/pulse/claudes-outages-show-dark-side-ai-productivity-total-system-lam-osbjc/>)，说某些开发者和工程团队已经完全停工。他们的工作流，乃至他们自己的编码能力，已经发展到高度依赖这些供应商的地步。原本只需要键盘和文本编辑器就能施展的技能，突然变成了必须订阅某家 AI 模型服务才能使用的东西。

顺着这个趋势想下去，并不难想象：我们可能正在创造一个行业，在这里，过去依靠独立思考和解决问题能力完成的事情，如今却必须通过付费购买 Token 才能完成。这有点像“供应商锁定”，但被锁住的是整个行业的技能体系（我敢肯定，模型供应商想到这里，正[兴奋地搓着手](<https://giphy.com/gifs/giphyqa-g0JP0HG6zF0o8>)）。无论是资金层面，还是智力与技能层面，这种支撑都可能随时被抽走；而本地大语言模型还远远没有准备好承接如此规模的需求。因此，我这里说的并不是被某一家具体供应商锁定，但“供应商锁定”这个概念，仍然与我们所看到的对这些系统的过度依赖密切相关。

这不是纯粹的理论猜测：如今就已经有人在[报告这种情况](<https://www.youtube.com/watch?v=5HaQnIPrfKk>)。甚至模型提供商自己也在揭示这一问题。Anthropic 的另一项[研究](<https://www.anthropic.com/research/AI-assistance-coding-skills>)显示，调试技能出现了高达 47% 的骤降：

> “在工作场所大规模引入 AI，尤其是在软件工程领域，必然伴随着取舍……开发者可能依赖 AI 快速产出结果，却因此牺牲了关键技能的培养——尤其是当事情出错时进行调试的能力。”

### 你没法预测自己的 Token 成本 {#section-10}

模型提供商正在接受[巨额补贴](<https://www.theverge.com/ai-artificial-intelligence/917380/ai-monetization-anthropic-openai-token-economics-revenue>)，模型本身也像建在流沙上。每次发布新模型，都重复着同样的循环：基准测试成绩亮眼，接着市场热炒，然后用户在实际使用中碰到现实，开始抱怨模型被“削弱”（nerfed），完成同样的工作却要多烧两三倍 Token。

你知道雇员要花多少钱，却不知道 Token 的费用会在每天、每月、每年发生怎样的变化。如果整个团队默认采用智能体编程，你的费用预算就得一直保持极高的弹性。正如 ThePrimeagen 最近[所说](<https://www.youtube.com/watch?v=_vB0PDzaa7I&t=3299s>)：“当你使用这些完全由智能体驱动的工作流时，模型供应商实际上就控制了你。”

当然，有办法避免这一切。大语言模型是一项极具威力的技术进步。如果使用得当，它们完全可以成为帮助人学习、提升技能的绝佳工具。它们让我能够更深入、更广泛地钻研各种概念和技术，扩大自己的理解范围，也让我得以探索那些过去实验起来既困难又耗时的新想法。我认为，这才是它们能为整个行业带来的最有长期价值的贡献。

## 我的做法：降低 AI 的角色地位 {#section-11}

我当然不是在主张，所有代码都必须靠人一个字一个字地敲出来。程序员一直都在想办法不必亲手写下每一行代码，就能*创造*出代码。这也正是我们会有 [Emmet](<https://code.visualstudio.com/docs/languages/emmet>)、自动补全和代码片段（snippets）的原因。就连 COBOL 当初的设计，也是为了用 `MOVE`、`WRITE` 这类近似英语的关键词，以更少的输入表达更多指令。jQuery 的口号更是“[写得更少，做得更多](<https://brand.jquery.org/logos/>)”（write less, do more）。大语言模型只是这一整套代码生成工具中的又一位新成员。

但我真正主张的是：**让大语言模型和编程智能体担任辅助角色，而不是为了生产力，把个人技能当成祭品。** 你完全可以把流程反过来：让它们在规划阶段协助头脑风暴，而你自己始终深度参与实现，只在有需要时才把任务委派给它们。这样既可以享受生产力提升，又能减轻理解债务（comprehension debt）。

### 我的日常工作流 {#section-12}

- **我让大语言模型协助生成规格说明和计划，由我来主导实现。** 这和“编排者”工作流刚好相反；视任务而定，我仍然亲手编写 20% 到 100% 的代码。
- **和模型协作时，我经常会先写伪代码。** 这样能缩短需求与最终生成代码之间的距离。
- **我把模型当成按需委派任务的工具。** 它们可以临时生成代码、充当交互式文档，也可以作为研究工具，让我不断提问、迭代、重构，并理清自己的实现思路。[关于任务委派的延伸阅读](<https://cheewebdevelopment.com/dont-vibe-code-delegate-responsible-development-with-llms/>)
- **我绝不一次生成超过自己能够一口气审查完的代码量。** 如果内容太多，我就放慢速度，把任务拆小，必要时亲自重构，确保最终能够完整理解结果。
- **我绝不会让大语言模型或智能体直接实现自己从未做过、也没有能力独立完成的东西。** 只有纯粹出于学习或教程目的时，我才可能例外，而且这类代码往往随后就会被丢弃。

如果一定要把这份清单压缩成一句话，那就是：**把它们当成《星际迷航》里的舰载计算机，而不是 Data（数据少校）。**（《星际迷航》的粉丝应该懂这个梗。）

### 我没有变得更快，但我正在做质量更高的工作 {#section-13}

这些模型带来的生产力提升是真实的；**而经常亲手参与工作所带来的磨炼，以及由此获得的理解，同样是真实的。**

过去，人们无数次试图让不懂编程的人也能轻松编程，但都未能真正解决这个问题。如今摆在我们面前的现实仍然是：**不亲自接触代码，就不可能真正理解代码。** 而且现在已经越来越清楚，如果你不再持续地接触、编写代码，就可能渐渐失去这份理解。讽刺的是，这最终会让你连“编排者”都当得越来越差，使当前这轮 AI 编程热潮成了一段古怪而又徒增压力的插曲。

### 或许是我担心得太多，但历史值得借鉴 {#section-14}

这一切总让我觉得似曾相识，仿佛我们又在自己身上进行另一场大规模实验。社交媒体刚出现时，我们同样没有弄清楚它的长期影响，就大规模投入使用；如今，我们已经面临普遍的注意力缺失等诸多问题。

而这一次，我们拿来下注的，是风险大得多的东西。

> “现在就全面押注 AI 智能体的人，无异于在确保自己终将被淘汰。如果你把所有思考都外包给计算机，你就会停止提升技能、停止学习，也不再变得更有能力。”
>
> —— Jeremy Howard，[fast.ai](<https://www.fast.ai/about.html>) 创始人
